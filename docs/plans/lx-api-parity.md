# LX 脚本 API 对齐与隔离边界（用户授权后）

## 1. 用户授权决定（2026-10-11）

用户明确要求「参照原 lxmusic，放开权限至这些源都可运行，只需要做好环境隔离即可」，并在澄清中确认：**全部放开**——包括脚本自身涉及内置卡密激活、QQ「越权/伪造 cookie」、DRM/ekey 解密的源，也按 LX 原样执行。

执行条件由用户在同一次澄清中给定：**逐脚本审批 + 环境隔离 + 如实报告结果**。本条与早期「不绕会员/DRM/登录权限」规则冲突，以本次授权为准，且本条为该冲突的唯一依据来源；后续如有变化，必须再次由用户明确修改。

## 2. 实现边界（不因放开而越界）

- 本路线只做**与原 LX 脚本 API 对齐**：实现 LX 自身提供给脚本的能力（utils、请求面、事件面、平台注册、脚本信息）。**不新增** LX 没有的破解/绕过能力，不为通过而改写第三方脚本或其接口地址。
- 风险由「拦脚本」转为「隔离 + 披露」：脚本按其自身逻辑行事，我们负责沙箱、权限最小化、网络约束、可撤销与可停用，并如实报告结果（不美化、不把 blocked/失败写成成功）。
- 若某脚本行为超出原 LX 能力范围（例如要求我们放宽私网、注入宿主凭据、关闭 sandbox），一律拒绝并报告。

## 3. 保留的隔离不变量（不得取消）

1. 独立非持久 session；`sandbox=true`、`contextIsolation=true`、`nodeIntegration=false`；页面 Node 关闭。
2. 专用 preload，realm 内只暴露 LX 约定 API，不暴露宿主文件系统/应用桥。
3. 逐脚本 SHA-256 绑定审批（digest/reviewVersion/riskVersion/acknowledged），摘要变化必须重新审批；导入不执行、重启不自动执行。
4. 网络：全部解析地址先做安全检查，连接固定到已验证公网 IPv4，重定向逐跳重新授权，超时与响应大小上限、请求选项在授权/DNS 前置校验。
5. 媒体：独立于 API 授权的 session-only 精确域名授权、opaque 挑战、token 签发与撤销、未知重定向即停。
6. 撤销与停用：拒绝/超时/停用/删除/重启/重新导入/脚本变化均 fail-closed 并撤销 token 与挑战。
7. 宿主侧逐脚本资源与消息预算（请求数、消息大小、并发、超时）。
8. 校验与审计手段（AST、静态审查、危险行为报告）仍可作为提示存在，但**不再是运行前提**；其结论与局限必须如实标注，不得冒称安全证明。

## 4. 对齐清单与切片

**切片 A：请求面（部分已落地）**
- headers：放开为按 LX 语义透传任意头（值仍校验类型与长度上限）；仅排除传输层必备头（Host/Content-Length/Transfer-Encoding/Connection 等由宿主接管）。已落 `referer`/`origin`，需扩展至 cookie、x-card-key、x-api-key、x-request-key、x-requested-with 等。
- body：字符串、对象（JSON）、表单、**formData/multipart**（LX 语义）；字节上限保留。
- 代理：LX 支持脚本环境代理与 `proxy` 选项；是否对齐需单独评估（涉及绕过网络策略，列为待决项并单独报告）。

**切片 B：`lx.utils` 对齐**
- crypto：`aesEncrypt`/`rsaEncrypt`/`md5`/`randomBytes`（宿主计算 + 有界 base64 桥接，避免 realm 内 Node 模块）。
- buffer：`from`/`bufToString`；zlib：`inflate`/`deflate`（同上，二进制通过 base64，且有大小上限）。
- 预算与错误语义按 LX 对齐，失败不得静默成功。

**切片 C：事件与 UI**
- `updateAlert`（有界内容 + 授权 + 展示）、`showConfigView`（配置视图注册与呈现）、事件返回值与 Promise 语义。
- 相关 UI 键必须三语言（en/zh-CN/in）。

**切片 D：未知动态域名的运行时审批**
- 与媒体审批同模式：脚本请求未知 API 域名时暂停并请求用户对**精确域名**明确确认，跨摘要/过期/停用即失效；不自动扩域。用于处理「静态无法预审的聚合接口」类源。

**切片 E：平台面（第 ⑤ 步）**
- kw/kg/tx/wy/mg/local 的声明、映射与调用链；需与 Omni/现有 provider 对齐，单独设计，不得一次全开。

## 5. 验收方式

每个切片：先写测试 RED → 实现 → GREEN；用自有 fixtures 覆盖真实语义与失败路径；真实 Electron（Xvfb，sandbox 不降）实跑；随后独立规格审查 → 独立质量审查；通过后提交并回读远端 SHA。全量 24 源复测作为端到端证据，逐源报告导入/初始化/接口/审批/token/播放，**blocked 与失败分开记**，不得混计或概括为「全部正常」。

## 6. 待决与风险披露

- 代理选项（切片 A 中的 `proxy`）可能让脚本绕过既有网络策略，需单独决策，默认不实现。
- 执行含卡密/越权/DRM 逻辑的脚本会产生对第三方服务的实际请求；结果如实报告，不承诺可用性或长期有效性。
- 词法审查为提示性信息，不是 AST/安全证明；WebRTC 旁路、浏览器不继承原 QuickJS 资源预算、`render-process-gone` 仅信号注入等既有边界继续披露。
